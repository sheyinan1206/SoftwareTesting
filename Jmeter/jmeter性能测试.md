# 一些常用参数

- 执行压测

基于 RPS模式 的压测 -- 性能压测场景的描述 -- 描述 压力值

*Request Per Second，每秒请求数

- 结果

  - 吞吐量（TPS/QPS） -- 系统性能指标
  
  - Transactions per second 每秒处理的事务数 或 Query per second 每秒处理的查询数（一个事务往往有多个请求）
  
  - RT -- 系统性能指标
  
  - Response Time，响应时间 -- 错误率、资源占用率

- jmeter线程工作模式

  - 第一种：指定jmeter 一个线程执行多少次请求【固定次数/不固定次数】
  - 第二种：jmeter压测时间
 
- 控制线程数量

    - 并发量：业界 1s内 服务器收到多少次请求 -- 3000/s
    - 线程数量理论计算公式=并发目标/单线程能够发起的请求
    - 单线程能发起的请求了：
      - 直接用一个线程 去压测一段时间
      - 1000 ms / 单词请求（响应）的时间

   > 总结：实际性能测试中，很难得出精确的线程数量

 - jmeter插件
   - 先下载JMeterPlugins-Manager.jar
   - 然后下载custom thread groups jar包
   - 梯度压测（jp@gc - Stepping Thread Group）：动态变化线程数量（例如：慢慢增加线程数量）
     - 线程总数的上限 - 大一点
     - 每个 10s 增加 2个 线程
    
 - jmeter性能测试过程中监控
     - 检查线程的运行状态 - Active Threads Over Time
  
 - **三大 性能指标**
     - 吞吐量
         - 【默认】按照请求数量划分：QPS、TPS
             - 吞吐量 -- 服务器每秒能够处理多少请求
             - 吞吐量=总的请求成功数/压测时间
             - **吞吐量越大，性能越好**
                 - 吞吐量相对稳定，或者变低 -- 达到系统性能瓶颈
                 - **吞吐量变化规律**：
                     - 波动很大 -- 代表性能不稳定
                     - 慢慢变高 -- 和并发量强相关
                     - 慢慢变低 -- 
          
         - 按照 网络数据包划分：KB
             - 现在 很少出现网络带宽不够的问题，现在都是动态申请为主
  

     - 响应时间：**系统快不快**
         - 响应时间超过了要求，代表系统到了瓶颈
         - 性能要求：产品、业务、技术负责人
         - 注意事项：分析在多少线程的情况下发生了超标
         - 响应时间变化的原因
             - 系统不稳定，有时快有时慢
             - 随着并发压力变大而慢慢变慢，响应时间变高
          

     - 错误率
         - 高并发场景下，系统是否能够正常处理业务
         - 要求：99.99%可靠，99.9999%
         - 错误率很高：
             - 接口请求错了
             - 服务器处理不了（达到了瓶颈 -- 代码，硬件资源）
             - 后端系统**限流**（系统配置了不能超过多少并发）

 # 实际问题

 ## RPS要贴近实际场景需求
 1. 压力过大，服务器崩溃，性能测试拿不到合理数据
 2. 压力过小，压测失去意义

举例：目标模拟20RPS

  问题：20个线程1s内发起了4000多个请求

  1. 接口很快，1个线程在1s内发起多个请求 -- （让他慢下来，或停下来）
  2. 接口很慢，一个接口请求3s中，发生什么情况？ -- RPS出现低估（所有线程都没空）
  3. 解决思路：请求很快，停一停。请求很慢，调度其他线程来请求

> 线程数量 = RPS目标 * 最大响应值（一个请求的时间 -- 例：3s）  搭配 吞吐量定时器（控制每分钟的请求量）
> 最大响应值时间值（事务-多个接口） -- （1.保守：产品意义上 2.激进：技术负责人）
